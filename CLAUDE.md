This file gives Claude Code context and guidance for working on this project. The project name is still undecided, so it's referred to as "PersonalColor App" as a placeholder throughout this document.

Project Overview

A personal color diagnosis + hair designer matching app for the Australian market, inspired by Korea's FACEBOARD (personal color diagnosis + KPCA-certified designer/salon directory app). Starts with a self-curated designer network, with no external certification body affiliation.

Core user flow

(Optional free entry point, added 2026-08-04) From the home screen, the undiagnosed clip run — live camera, eight colours under the chin, no photo taken and no API call. It names no winner and ends on a CTA into the flow below. It is the cheap top of the funnel, not a step in the diagnosis; see "Result Screen and Sharing Surfaces".
User takes/uploads a photo
AI runs an initial personal color diagnosis pass (4 season types: spring warm / summer cool / autumn warm / winter cool, plus subtypes)
User confirms/refines the result through 2-3 rounds of digital draping — picking between paired color swatches shown next to their photo — and the final season type combines the AI's initial read with the user's picks
Diagnosis result is rendered as a shareable card image
Matching hair designers/salons are recommended, with a way to make contact

Access tiers, as built (2026-08-05)

- OPEN, no account: the clip run (`/clip`, both modes) and the home screen. Nothing it does costs money — no photo, no upload, no API call.
- ACCOUNT REQUIRED: everything else. /api/analyze, /api/upload, /api/card and /api/save all call `requireUserId()` from lib/server/auth.ts and 401 without a Bearer token. Those four are the routes that spend real money (Claude per analysis, Creatomate per card, R2 per upload) and three of them were fully anonymous until this date — anyone holding the URL could spend the budget. The UI gate on the home screen and the `Redirect` in capture.tsx are conveniences so a signed-out user is not walked to a shutter that can only fail; the server check is the actual gate, and removing it is not a UI decision.
- Rate limiting sits on top, per user, in `enforceRateLimit()`. It is IN-MEMORY and therefore per-instance: the real ceiling is the limit times the number of running instances, and a cold start resets it. It is a speed bump against one runaway account, NOT a spend cap. The durable version is the deferred credit ledger.
- The guest machinery is now UNUSED but deliberately kept: `diagnoses.user_id` is still nullable, `claim_diagnosis()` still exists, and the pre-Phase-5 claim-token TODO in 0001_init.sql still stands. Do not delete them to tidy up — the login wall is a product decision that Phase 6 completion-rate numbers could reverse, and the cost of keeping unused DDL is nil next to rebuilding it.
- Account deletion is a REQUIREMENT, not a feature: App Store Review Guideline 5.1.1(v) means an app that creates accounts must delete them in-app, and review checks it. It lives at the bottom of history.tsx → DELETE /api/account → `delete_account()` then Clerk `deleteUser`. That ORDER matters: our rows first, Clerk second, because once the Clerk user is gone the caller has no token and could never retry. Do not "optimise" it the other way.
- ACCOUNT DELETION IS THE ONE PLACE THIS PROJECT HARD-DELETES — a deliberate, scoped exception to the "soft delete only" rule above, decided 2026-08-05. That rule is a data-hygiene convention, not an answer to a legal deletion requirement: tombstoned rows are invisible to the app yet still sitting in the database, which is weak against Apple's guideline and against APP 11's expectation that personal information no longer needed is destroyed or de-identified. DO NOT GENERALISE IT: individual diagnoses are still soft-deleted via `soft_delete_diagnosis()`, and every other table keeps `deleted_at`.
- Two tables are DE-IDENTIFIED rather than deleted, and the distinction is the point: `designer_clicks` and `directory_views`. What belongs to the user is WHO clicked, not THAT a click happened — deleting the row would silently shrink a designer's invoice and corrupt the city-demand signal, i.e. erase a third party's record of service delivered. Nulling `user_id`/`diagnosis_id` satisfies the deletion request while the row, its `designer_id` and its timestamp survive. Accepted cost: clicks from deleted accounts can no longer be counted as UNIQUE users, only as total clicks — billing is on totals and deletions are a rounding error, so a pseudonym column would encode a metric decision nobody has made. Any future table carrying a user id must pick one of these two treatments explicitly, inside `delete_account`.
- HARD DELETION COST US THE TOMBSTONE THE RACE GUARD RELIED ON, hence `deleted_accounts`. A soft delete left a `deleted_at` that write paths could check; deleting the row removes it, so a request already in flight can recreate the account through 0001's upserts before Clerk's `deleteUser` lands. `deleted_accounts` holds nothing but a Clerk `sub` that no longer resolves to a person, kept solely so the `users_block_deleted` trigger can refuse to recreate it — the standard suppression-list pattern. `users.deleted_at` is now vestigial: nothing sets it, and the column stays only because 0001's RLS policy references it.

Architecture Conventions (project-wide rules)
Soft delete only — no table is ever hard-deleted. Use a deleted_at column.
RLS uses auth.jwt()->>'sub' — not auth.uid(), since auth is via Clerk.
SECURITY DEFINER functions always specify SET search_path = public.
All monetary values are stored as integer cents (applies once Phase 5 payments are introduced).
Folder structure follows Expo Router's default convention (app/ directory-based routing).
Mandatory Error Handling Rules (절대 규칙 — non-negotiable)
These rules apply to ALL backend/API code (API routes, Inngest jobs, Supabase functions, server-side scripts). Code that violates any of them must not be submitted.
- Every error thrown from business logic is an AppError carrying a machine-readable code, an HTTP status, and optional details. Never throw raw strings or bare Error objects.
- Error categories are kept separate, each with its own code and status: validation (400), auth (401), forbidden (403), not_found (404), conflict (409), rate_limit (429), internal (500). Never collapse everything into a generic 500.
- A single global error handler maps AppError → HTTP response. No ad-hoc per-route try/catch response shaping.
- Every request gets a requestId (generated at entry, or propagated from an incoming header). It is included in every error response and every log line for that request.
- Production error responses must NEVER expose stack traces, SQL, internal error messages, API keys/secrets, or infrastructure details. Clients receive only: code, a safe user-facing message, requestId, and field-level details for validation errors.
- Every error log includes: requestId, user/tenant identifier, request path, error code, and the full stack trace. Detail belongs in logs, never in responses.
- Error-handling behavior must be covered by tests (correct status/shape per category, no internal leakage in production mode), and code is only submitted when those tests pass.

Data Model (implemented — supabase/migrations/ is the source of truth)

The schema lives in supabase/migrations/0001_init.sql and 0002_allow_skip.sql, and has moved past the original draft. Read the DDL before changing anything; the notes below are only the parts that are NOT obvious from reading it.

- Write model: diagnoses / drape_responses / photos are written ONLY by the server (service role), through persist_completed_diagnosis(), which persists a finished diagnosis and its draping rounds atomically and idempotently (re-submitting the same pre-generated id is a no-op). Clients never insert results, and the server recomputes the final season before persisting. This is the tamper-proofing that Phase 5's paid diagnoses depend on — do not add a client write path.
- Guests: diagnoses.user_id is nullable. After login a guest row is attached via claim_diagnosis(). For the MVP the bare diagnosis UUID is the claim capability; before Phase 5 it must become a hashed one-time token with an expiry (TODO recorded in 0001_init.sql).
- diagnoses carries more than the draft did: llm_runner_up_season_type, is_borderline, final_confidence, combination_method — plus CHECK constraints pinning subtype to its season and forcing draping_shifted to land on the runner-up. The DB is the last line of defence behind combine(), not the only one.
- drape_responses.user_choice is a | b | skip. Skips are recorded (a high skip rate flags a bad swatch pair for palette tuning) but count as no vote in combine().
- photos rows are service-role only and hold just the R2 key + expiry. The object is deleted in /api/analyze the moment analysis finishes, success or failure; the bucket lifecycle rule is the backstop, not the primary mechanism.
- designers exists with a GIN index on specialties, but is empty — Phase 4 has not started.
- final_confidence is still written and still computed, but is NOT displayed anywhere (see "Confidence is a band, not a percentage"). history.tsx deliberately does not select it. Keep storing it — it is the raw material the consistency test will calibrate.
Result Screen and Sharing Surfaces

Three distinct surfaces, each with a different job. They look similar and are easy to confuse when editing.

- components/drape-compare.tsx ("SEE IT ON YOUR SKIN") — the DIAGNOSTIC one. The photo already taken, fabric at the neck, a draggable divider wiping between the season's signature colour and its sharpest avoid colour. The face is never split down the middle: that would compare one cheek under one colour against the other cheek under the other, and faces are neither symmetric nor evenly lit. Clipping is done with two counter-translating transforms rather than an animated width, because animating width re-runs Yoga layout on every touch frame and the wipe visibly stutters. It also lives inside a ScrollView, so its PanResponder claims only on horizontal intent and refuses termination — without both, the two fight over every drag.
- app/clip.tsx ("MAKE A CLIP") — the PROMOTIONAL one, and the only one meant to be filmed. Live front camera, a fabric-shaped colour band swapping under the chin on a beat, the way a consultant works through drapes. Nothing is captured, uploaded or stored — it is a viewfinder with an overlay, and the user's own screen recording is the artefact. Flow is ready → 3-2-1 countdown → run; the countdown is NOT automatic on entry because starting the OS screen recorder takes several taps and a countdown that fires first is worse than none. A neutral grey "cape" shows during ready so the user can line their chin up without seeing a colour early.
  This screen runs in TWO modes off one flag — whether `useFlow()` has a result. It is the same component, and edits touch both. Do not re-add the `if (!result) redirect` guard that used to sit at the top.
  - PERSONALISED (entered from result.tsx): the victory lap. Season stamped on the frame, tick/cross per swatch, `temperatureRun(season)`, and it LOOPS so several passes fit in one screen recording.
  - UNDIAGNOSED (entered from the home screen): the free front door — no photo, no sign-up, no API call. `neutralRun()`, no season stamp (the chip reads "Warm or cool?" instead), no tick/cross, and it ENDS on a CTA card rather than looping.
  The undiagnosed mode withholds the verdict ON PURPOSE, and that is the whole design. The user sees a difference they cannot name, and that gap is the reason to go on to the paid analysis; a free run that answered the question would close the funnel instead of opening it. `NeutralSwatch` therefore OMITS `suits` rather than setting it false — the screen keys the tick/cross off `'suits' in swatch`, so the field's absence is what enforces this, and a test pins it. If you ever want the free run to give a hint, that is a pricing decision, not a copy tweak.
  The colour advance is a chained setTimeout keyed on `index`, not one setInterval: the last swatch of an undiagnosed run has to end the run instead of wrapping, and it also means tap-to-skip restarts the hold instead of inheriting whatever was left on a shared interval.
  FACE GUIDE AND DRAPE GEOMETRY ARE COUPLED ON PURPOSE (added 2026-08-04). `DRAPE_HEIGHT` / `DRAPE_OVERHANG` / `DRAPE_TOP` / `CHIN_GAP` / `CHIN_LINE` are named constants at the top of clip.tsx, and the guide oval is positioned so its BOTTOM EDGE IS the fabric line. Do not re-inline the drape's height or offset — the guide is computed off them, and hardcoding one silently teaches framing the other no longer matches. The oval is anchored to the fabric rather than centred on the screen because the relationship is the whole point: a drape works by sitting directly under the jaw and bouncing colour up onto the skin, so a face floating mid-frame with a band somewhere below it is the wrong shot and reads as a filter. CHIN_GAP is small (1.5% of height) for the same reason — a bigger gap is a weaker effect, not a tidier layout.
  Shot-quality layers added 2026-08-04, all in clip.tsx. In render order: colour SPILL (the current swatch bleeding up from the fabric, `SPILL_HEIGHT` / `SPILL_ALPHA`, running only) → VIGNETTE (dark corners, always) → drape → BLOCK FLASH (a full-frame wash of the incoming colour plus a scale pop on the caption, fired only at `index === swatches.length / 2`). The spill rises from the fabric rather than glowing from every edge because that is the direction real bounced light comes from; it is the low-risk, perceptual-only half of the still-open "should the clip light the face" question and does NOT settle it. The block flash exists because the midpoint is the one cut that means something — within a block the hard cut stays, and crossfading colours was considered and rejected as it blurs the contrast the clip exists to show.
  clip MUST stay registered in app/_layout.tsx with `headerShown: false`. It was missing until 2026-08-04, and an unregistered expo-router route silently falls back to the DEFAULT header — a "< index / clip" nav bar was sitting at the top of the screen, eating roughly 230px and pushing every absolute overlay down, so the geometry above did not land where its arithmetic said. Nothing errors when this entry is dropped; the screen just quietly grows a header that ends up in every recording. The screen has its own exit control, so the header's back button is redundant anyway.
  Layout rules that were learned the hard way on that screen: the top row uses `items-center`, not `items-start` — the two pills are different heights (bold body label vs small-caps wordmark) and top-aligning them leaves the type visibly off a shared line. `MARK_INSET` adds clearance inside CROP_SAFE so marks are not flush against the cut line. The face guide carries NO caption: it used to repeat the ready panel's opening sentence verbatim, and its position floated with the oval height, so on shorter screens it crowded the top chips. The ready panel's bottom padding clears `cropBand` so Begin never sits inside the strip labelled as being cropped, and it is `bg-black/70` rather than the /45–55 used elsewhere because it lands on the pale cape, not on live footage.
  DARK CHROME IS NOT AN OVERSIGHT — do not "fix" it for consistency with the rest of the app. Every pill, caption and crop band on this screen is bg-black/45–55 with white text because it sits over a live camera feed of an unknown room; users are coached to find bright light, so light-on-light is the common failure and only white-on-dark survives every background. Two surfaces are deliberately light instead (2026-08-04): the root container, which the camera covers within a frame and whose only job is to not flash black on the way in from a light home screen, and the `done` CTA card, which covers the feed almost entirely so the legibility constraint does not apply — it is the most-screenshotted frame and the handover back into the app. Both use `bg-background`, not literal white, so dark mode still works. The CTA card is fully OPAQUE by necessity: tailwind.config.js defines `background: hsl(var(--background))` with no `<alpha-value>` slot, so `bg-background/95` cannot be generated and would drop the fill rather than soften it. The vignette sits at 0.4 (down from 0.6) — enough to keep the face and fabric the brightest things in frame without the screen reading as heavy.
  react-native-svg is used for real now (the spill and vignette gradients). Its documented first-stop gotcha therefore applies to live code again, not just the deleted compositing surface: BOTH gradients carry an explicit offset-0 stop, and removing one silently blanks the whole lower range.
  HOLD_MS IS UNIFORM AND MUST STAY UNIFORM. Varying it per colour was proposed and rejected: on the undiagnosed run, holding one temperature longer IS a verdict, and that run withholds the verdict by design. `NeutralSwatch` omitting `suits` guards the tick/cross, but nothing guards the edit — a single constant is what stops the timing from implying a winner. (The proposal also claimed it would shorten the run; 4x900 + 4x1500 is 9.6s, exactly what 8x1200 was.)
  The uniform VALUE is 1000ms (lowered from 1200 on 2026-08-04), chosen for the platform rather than for draping: eight colours land the run at 8s / 11s including the countdown, which keeps completion rate — short-form's strongest ranking signal — in reach, and 1000ms is exactly two beats at 120BPM, so the eight swaps fill four bars and any trending audio dropped over the clip cuts on the beat and ends on a phrase boundary. Still unverified on a real device: whether 1000ms is long enough to read the skin's reaction is the open question, and lengthening it back is the fix if not.
  TYPOGRAPHY IS SIZED FOR A FEED, NOT FOR THE HAND HOLDING THE PHONE. The WARM/COOL word is text-4xl because it is the only thing a stranger reads and it has to survive a screen recording, the platform re-encode, and thumbnail-size viewing. The countdown deliberately INVERTS the obvious hierarchy — hook large, digit small — because the digit is for the person filming and the hook is for everyone who sees the post, and a huge "3" is the opening frame of the recording. Same reasoning on the `done` card: the question is large and the CTA buttons are demoted, because whatever is on screen when recording stops is the post's last frame, and "which half?" is what a viewer answers in the comments — comments being the reach mechanism the clip exists for. The card repeats BrandMark since it is opaque and covers the one at the top of the screen. Do not "rebalance" any of these toward the operator's convenience; they are aimed at the audience.
  The countdown carries the hook text, not just the digit — it is the first frame of the recording, short-form autoplays muted, and a bare numeral spends the most valuable second on nothing.
  Crop bands (`REEL_ASPECT`) are shown during `ready` ONLY, and measured from the real screen rather than assumed: phones vary, and a 16:9 device like the SE crops nothing, so the bands are suppressed when `cropBand` rounds to zero. They inform framing and never actually crop. CROP_SAFE stays as the conservative band the marks sit in; on every device checked it is the larger of the two.
  The guide is drawn during `ready` and `counting` ONLY, never during `running`. This screen exists to be filmed and a guide left in frame is a guide left in the post; the countdown is kept as an exception because those seconds are the framing window and are leader footage the user trims anyway (the 3-2-1 is already in them). If a new phase is added, decide which side of that line it falls on.
- components/post-sheet.tsx ("POST YOUR CLIP") — the handover, added 2026-08-04. Reached from the `done` card and from a Post pill in the chrome during a run (the personalised run loops and never reaches `done`, so without the pill the more postable of the two modes would have no route at all).
  It hands the file back rather than producing one, and that is forced by the architecture: the app never records, so the artefact is the user's own OS screen recording and it already lives in Photos. The sheet opens the SYSTEM PICKER (expo-image-picker, videos) and passes whatever the user selected to the native share sheet (expo-sharing), where Reels / Shorts / TikTok appear. No media-library permission is involved — the picker only ever returns what was explicitly chosen — so this does NOT reopen the expo-media-library removal.
  Do not "improve" this into in-app recording with expo-camera's recordAsync. It records the CAMERA STREAM, so the drape colour, the captions and the brand mark — everything that makes the clip a clip — would be absent from the file. Real one-tap capture needs a screen-capture API the app drives itself (ReplayKit / MediaProjection), which is a native module and a config plugin, cannot be built or tested on this machine, and is the only thing that would actually make posting one tap.
  The caption is written for the user because choosing one is the step that actually stalls people. It opens on the question, not on the product, since comments are the reach mechanism. Both spellings of the tag ship together — the market is Australian and writes "colour", the tag volume sits on "color" — and #shorts is what makes YouTube file an 11s vertical clip as a Short. Copy is press-and-hold on a `selectable` Text rather than a button: one-tap copy needs expo-clipboard, a native module, and a new dev-client build for a convenience.
  Opening the sheet freezes the run (`postOpen` guards the advance effect) so a neutral run cannot quietly end while the user is away in the picker.
- The Creatomate card (/api/card) — metadata only, never the face, so it is safe to keep and share long-term.

An earlier fourth surface slid a masked photo across two fixed colour fields. It was deleted. Compositing a still onto a colour needs the face cut out of its background, and with no person segmentation available the feathered oval standing in for a cutout read as a ghost. The live camera version has nothing to composite, which is why it replaced it — do not reintroduce the photo-compositing approach without real segmentation.

Gotcha worth keeping: react-native-svg does NOT extend a gradient's first stop back to offset 0 the way the SVG spec says. A radial-gradient mask whose first stop is at 0.8 leaves the entire core transparent, so only a thin ring renders. Always write an explicit offset-0 stop.

The clip run is warm colours then cool colours (lib/diagnosis/recommendations.ts: TEMPERATURE_DRAPES), not the season palette. Temperature is chosen over season because undertone is the axis the diagnosis turns on and the only one a stranger scrolling past can read — "warm vs cool" lands, "terracotta vs icy pink" does not. The cost is that depth and chroma drop out, so the clip communicates "cool" rather than "summer"; the season name stamped on the frame carries that.

Both modes draw the same eight colours from TEMPERATURE_DRAPES — the free run is not a lesser preview, and a test pins that. Only the ORDER differs, and each order has its own reason:
- temperatureRun(season) OPENS on the opposite temperature and CLOSES on the user's own. The payload is the result, so it should end on the confirmation, and a shot where you look good is the one that actually gets posted.
- neutralRun() is a fixed warm-then-cool for every user, because there is no season to close on and a run that differs per user is not a recognisable format. The known cost is that the cool block gets a recency advantage in the viewer's own judgement; accepted, because this run is a hook and never a measurement. Do not "fix" it by randomising.
Tests pin both orderings.

Letting users hand-pick the colours was considered and rejected: it puts a configuration screen in front of the fun, and the people least able to choose colours are exactly the ones using the app. Preset sets ("my palette", "best vs worst") are a reasonable v2 because they multiply the number of clips one person can make, but they are deferred until there is evidence anyone makes even one.

Attribution: components/brand-mark.tsx is the single stamp on everything postable. BRAND_NAME lives in lib/card/templates.ts so the Creatomate card shares it — changing that one string updates card, clip and stills together. BRAND_LOGO and BRAND_HANDLE are deliberate empty slots. A logo never replaces the wordmark (someone who sees the clip searches for a name, not a shape), and the handle stays null until the accounts exist rather than shipping one that 404s. Callers must keep the mark inside the crop-safe band — a phone screen is roughly 9:19.5 but Reels is 9:16, so about 9% off each end is cropped on upload, and a mark that gets cut off is the same as no mark.

Confidence is a band, not a percentage

The result hero and the card used to read "85% match". They now read "Strong match" / "Good match" / "Close call" via confidenceBand() in lib/diagnosis/combine.ts. The number was not a measurement:
- Nothing calibrates it. The Phase 1 consistency test has never run, so 0.55, 0.1, 0.08 and 0.95 in combine() are all hand-picked.
- It is not one scale. draping_shifted computes it from the vote margin alone and ignores the model's own confidence; llm_confirmed starts from that confidence and adds to it. Same number on screen, two different meanings.
- With three hardcoded rounds, draping_shifted could only ever emit 0.65, 0.75 or 0.85 — the percent sign advertised precision that was never there.

The bands are read off what actually happened instead: whether the photo read and the picks agreed, and by how much. Two rules are load-bearing and tested — a result that draping OVERRODE is never "strong" (the two signals disagreed by definition), and a photo read the model flagged is_borderline is never "strong" however lopsided the vote. Exact vote counts stay visible in the result details, so nothing is hidden, only un-dressed-up. Revisit once the consistency test gives the numbers meaning.

/api/card takes the band KEY and maps it to copy server-side, so a caller cannot stamp arbitrary text onto a shareable card.

Known dead code: the 0.9 ceiling in combine.ts's draping_shifted clamp is unreachable while rounds are fixed at 3 (max margin 3 → 0.85).
AI Diagnosis Pipeline Notes
Hybrid two-stage diagnosis: (1) a vision LLM gives an initial season-type read from the photo alone, (2) the user then confirms/refines it through 2-3 rounds of digital draping (picking between paired color swatches shown next to their photo). The final season type combines both signals — it is never based on the photo analysis alone.
This hybrid design is also a deliberate differentiation choice, not just a UX nicety: known Korean patents on automated personal color diagnosis (facial-region RGB extraction compared against a reference library; hexagonal color-model matching) claim purely photo-analysis-based methods. Layering user-driven interactive preference selection on top of the LLM's initial read is a materially different technical approach from those specific claims.
Original photos are deleted immediately after analysis completes (R2 lifecycle policy). Only diagnosis result metadata (season type, extracted color values, draping choices) is kept long-term — never the original face photo.
The line this draws is "does it contain a face": no face → the server may keep it (the Creatomate card does), face → device only. That rule settled two decisions. Consent-gated server retention of a face composite was considered and rejected — the delete in /api/analyze is unconditional (a finally block, success or failure), and that lack of a branch is doing real work as a safety property; a "Save" tap is also weak consent for storing a face image in the Australian market. And react-native-view-shot + expo-media-library were added for an on-device still export, then removed with the feature, along with the NSPhotoLibraryAddUsageDescription and Android media permissions prebuild had pulled in with them. If a consent-gated retention path is ever built, the thing that justifies it is photos for validating the diagnosis engine, not a promo image — and it needs its own clearly-worded toggle, not a Save button.
Specify color-theory criteria (warm/cool, depth, chroma) in the prompt and include few-shot examples to keep the LLM's initial read consistent.
If volume grows, consider prompt caching for the fixed, repeated part of the prompt (not needed at the current stage — per-diagnosis API cost is already in the 1-2 cent range).
ONE photo per diagnosis (decided 2026-07-29). A multi-photo ensemble (2-3 shots, majority vote) was considered and deliberately deferred: requiring several photos before the user sees any result attacks diagnosis completion rate, one of the three Phase 6 metrics, and the draping rounds already exist to absorb single-photo variance. Reversing it later is cheap — combine() takes one Analysis, so a merge step slots in ahead of it. Revisit only if the consistency test reports hybrid stability below ~85%, and note that the fallback of record at that point is the Lab-space two-stage classifier, not an ensemble.
The capture screen defaults to the FRONT camera on purpose, despite rear cameras being more color-accurate. Every item in the shot guide — oval alignment, shadow on the face, hair off the forehead, top color reflecting onto the neck — can only be verified live on the front camera, and bad framing or backlight damages the read far more than softer tone mapping does. A front-camera bias is also systematic across all users and therefore correctable in the prompt; a random front/rear mix is not. Do not "fix" this default to 'back', and do not write copy recommending the rear camera.
Shot guide (components/shot-guide.tsx): a bottom sheet over the live camera, shown every time the capture screen opens, and re-opened carrying the model's own image_quality.notes when a shot comes back with lighting_ok=false or face_visible=false. Input quality dominates everything downstream — a warm indoor bulb alone can flip a cool read warm, and the prompt's cast correction only goes so far — so coaching the shot is the cheapest accuracy available. Camera controls are disabled while it is open, because a plain View overlay does not claim touches in React Native.

CameraView takes NO children. expo-camera warns that children lead to inconsistent behaviour or crashes, and capture.tsx used to nest the alignment guide and the shutter controls inside it. Everything drawn over a preview is now an absolutely positioned sibling with the camera on StyleSheet.absoluteFill — follow that pattern in any new camera screen (app/clip.tsx does). The disabled-while-guide-is-open workaround above is unrelated and still needed.
Phase 1 Consistency Test — how to read it (it will quietly lie in three ways)
Always pass --truth. Without it the "true" season defaults to the majority LLM read (consistency.ts), so the simulated user agrees with whatever the model said most often and stability is inflated by circular reasoning.
Only feed it photos of ONE person. Stability is the share of photos agreeing with the modal season, which is meaningless across different people — and worse, if the model collapses everyone into one season it reports 100%, peaking exactly when the model is most broken.
Treat the number as an optimistic ceiling. simulatePicks() models a user who always picks their own season's swatch; real users are noisier and skip rounds. Use ~85% as the pass mark, not the script's built-in 80%.
Coverage/bias testing — do different people spread across seasons, does confidence drop systematically for deeper skin tones — is a DIFFERENT question needing a different harness, which does not exist yet. lib/diagnosis/color.ts (CIE L* from a hex) was added as its first piece. It now has a consumer: normalizeHex() was split out of lightness() and is what result-details.tsx runs observed_colors through, since the model writes those hexes free-form (bare, lowercase, or an empty string for a region it could not read) and a raw one reaching a style prop breaks the view.

App Store account transfer (likely, not certain — noted 2026-08-05)

The app ships from a PERSONAL Apple Developer account, and there is a good chance it moves to a company entity later. Transfer is supported by Apple and the app keeps its identity through it, so nothing here is a blocker — but three things are cheap now and expensive or impossible afterwards, and they should be decided with the transfer in mind rather than discovered at transfer time.

- BUNDLE ID IS THE ONE IRREVERSIBLE CHOICE. It is permanent once released AND it survives the transfer unchanged, so `com.developermo.colorapp` would leave a personal handle sitting under a company account forever. Changing it is one line today and impossible after the first release. This is the concrete reason the app name decision cannot slide past the first App Store Connect record — see "Project/app name" under Still Undecided.
- SIGN IN WITH APPLE MAKES THE TRANSFER NON-TRIVIAL, and we already use it (`oauth_apple` in app/sign-in.tsx, via Clerk SSO). Apple's user identifier (`id_token.sub`) and private relay address are TEAM-SCOPED: after a transfer they change, so a returning user looks like a new person unless they are migrated within the 60-day window (Apple TN3159). In this app that means Clerk mints a new user, and `diagnoses.user_id` — which IS the Clerk sub — no longer matches, so saved results are orphaned while login still appears to work. It is a silent data-loss shape, not an error.
  The chain worth knowing: offering Google login is what obliges us to offer Sign in with Apple (App Review 4.8 wants an equivalent privacy-preserving option). Dropping Google in favour of the existing email-code flow would remove the Apple requirement and the migration burden with it — at an obvious cost to sign-up conversion. Not a recommendation, just the lever, since nobody remembers it exists at transfer time.
- An app can only be transferred AFTER at least one version has been released. Whichever account publishes v1 holds it until then, so there is no "publish now, sort the entity out before launch" option.

Also worth remembering that the Apple transfer is only one of several: Clerk, Supabase, Cloudflare R2, Anthropic and Creatomate all have their own account ownership, and the EAS project (`@developermo/colorapp`) transfers separately from the App Store listing. Expo documents a project transfer and it is the easy one.

Two structures, and they behave completely differently — worth knowing before an accountant frames the move:
- ASSET SALE (a new company buys the app from the sole trader — this is what a personal → company move actually is): the ABN does NOT follow, so Apple needs its app-transfer process, Sign in with Apple needs the 60-day user migration, and Stripe is the open question below.
- ENTITY SALE (someone buys the company itself): the entity keeps its ABN and only its owners change, so no platform transfer happens at all — the Apple team does not change, which means the Sign in with Apple problem disappears entirely.
Building inside a company from the start therefore does more than avoid work now; it keeps the entity sale available as an exit structure later. Buyers may still prefer an asset sale, so it is an option gained, not a guarantee. How to structure it is accountant/lawyer territory — recorded here only for what each structure does to the platform accounts.

STRIPE: UNRESOLVED, and an earlier claim here was overstated. "Stripe requires a separate account per legal entity" is about running several entities AT ONCE and was wrongly applied to a sequential sale. Stripe's own transfer page shows legal business name and TAX ID are editable on an existing account, which suggests the account can survive an entity change — but the page does not say whether customers, active subscriptions, saved payment methods and history carry over, and that is precisely the question. It cannot be answered from documentation; ask Stripe Support directly. The answer changes how urgent incorporation is: if the account survives intact, Stripe stops being a reason to incorporate early and only the Apple reasons remain. Until then, note that the pain scales with the number of Stripe subscribers, which is designers only (deliberately a curated ~20–30), while consumer revenue runs through Apple IAP and transfers with the app.

DECIDED 2026-08-05: ship from the INDIVIDUAL Apple account for now. The company move stays open, and nothing about it blocks development.

The bottleneck is NOT the D-U-N-S number — an earlier version of this note said to apply for one early, which was wrong and is corrected here. Security invariants (migrations 0003–0005 — read before touching RLS or the deletion path)

These came out of a review; two were latent since 0001. Each is an invariant, not a preference.

- RLS RESTRICTS ROWS, NOT COLUMNS. A row policy alone would hand anon the whole published `designers` row including `booking_url` — so any client could read the destination from PostgREST and navigate there without calling the click endpoint, making the meter the entire listing fee rests on trivially bypassable. COLUMN-LEVEL GRANTS close it: the policy picks the rows, the grant picks the columns, and `booking_url` is served only by the click API, which logs first and returns the URL second. `contact_info` and `specialties` are withheld too. Never add a column to that grant without asking whether a client reading it directly breaks something.
- A DELETED ACCOUNT IS NEVER RECREATED, enforced by the `users_block_deleted` trigger against `deleted_accounts`. 0001's write RPCs upsert a users row on every call, so without it a request in flight during deletion simply rebuilds the account and writes under it. The trigger states the invariant once instead of rewriting ~200 lines of unrelated function body, and it catches write paths that do not exist yet. The concurrent save now fails, which is correct — it was doomed the moment deletion started.
- A USERS ROW IS CREATED ONLY BY `ensure_user()`. The directory tables carry a users FK and are reachable *without* a diagnosis (browsing, joining the waitlist), while until then a users row only appeared via `persist_completed_diagnosis` / `claim_diagnosis`. It uses `on conflict do nothing`, never 0001's `do update set deleted_at = null`.
- A WELL-FORMED R2 KEY IS NOT PROOF OF OWNERSHIP. `/api/analyze` used to read and then delete any key matching the pattern, and `/api/upload` recorded nothing, so a leaked key let one account analyse and destroy another's photo. Upload now writes a `photos` row via `claim_photo_key`; analyze checks `owns_photo_key` first and answers `not_found` on a miss so probing reveals nothing. The privacy story is unchanged — the object is still deleted the instant analysis finishes.
- CLERK TOKENS ARE PINNED TO `CLERK_AUTHORIZED_PARTIES` when it is set. Without an `azp` allowlist, a valid token minted for a different app on the same Clerk instance is accepted. Unset is correct for native-only development (no browser origin to assert); it must be set before any web surface ships.
- Also constrained at the DB level because the client opens these values or groups by them: `booking_url` must be `https://` (otherwise a listing is a redirect primitive aimed at our own users), locations must be non-blank after trim (blank values silently split a city's demand signal), `result_count >= 0`, and `published_at` cannot be in the future (the policy and index both key off `published_at is not null`, so a future timestamp publishes immediately).
- STILL OPEN, and needed before the click endpoint can bill anyone: the API must derive user_id from the JWT, verify the designer is published, verify the diagnosis belongs to the caller, be idempotent per request, and rate-limit durably — `enforceRateLimit` is per-instance and resets on cold start, as its own comment says. Raw row counts should not go straight onto an invoice.
- NOT VERIFIED BY EXECUTION: 0004 and 0005 have never been run. There is no psql, no Docker and no local Supabase CLI on this machine, and no DB connection string in `.env` — only the PostgREST keys. There are also no SQL/RLS tests. Before relying on any of the above, apply them and check the permission matrix per role (anon / authenticated / service_role), ideally with pgTAP plus Supabase's Security Advisor.

- SO STRIPE CONNECT IS NOT NEEDED. Money flows designer → us; we are the merchant. Connect exists to pay third parties out. The Phase 5 line above predates this. Also: Stripe bills cards worldwide from a supported merchant country, so the AU-only billing limit is a TAX decision (cross-border B2B VAT/GST), not a Stripe capability one.
- THE THRESHOLD IS NOT IN THE SCHEMA and must not be added until real click volume exists. Same failure mode as the hand-picked confidence constants in combine.ts. Charge manually from a spreadsheet at ~20 designers — the delta between charging and not is a few hundred dollars a month, far less than metering and dispute handling cost to build.
- DESIGNER-LEVEL LISTING, SALON-LEVEL BILLING. Clients follow a stylist, not a shop; booking URLs are often per-stylist; and a portfolio — the only credible specialty signal we will ever have — belongs to a person. `salon_id` is nullable because chair renters and mobile stylists are real. Location lives on the DESIGNER so an independent with no salon is still findable.
- SPECIALTY MATCHING IS DROPPED AND THE GIN INDEX IS GONE. Self-declared tags cannot work: no colourist declares themselves weak at a season, so every designer ends up with every tag. Matching is also a SCALE feature — at ~20 curated designers there is nothing to narrow, and showing all of them sorted by location is the correct product. When it becomes real it runs on portfolio EVIDENCE (which of the 16 hair colours in SEASON_RECOMMENDATIONS a designer has actually done), which needs a photo table, not the `specialties` column.
- The v1 promise is NOT "we matched you to the right designer" — it is "these designers understand personal colour results and will work from your card." That is what curation buys, and it is why publication stays gated.
- GLOBAL, ASYMMETRICALLY. Users: global from day one — the app already works everywhere except this one screen, and clips do not respect borders, so overseas users arrive whether planned for or not. Designer APPLICATIONS: global (free supply capture, and it solves the chicken-and-egg when demand and supply appear in the same city on their own). PUBLICATION: approval-gated, and held via `published_at` so a city opens with a handful rather than one lonely listing. BILLING: AU only.
- THE EMPTY DIRECTORY IS THE MAJORITY EXPERIENCE for a long time, not an edge case — design it as a real screen. The result screen must check before promising a designer; if the city is empty, the waitlist is the primary action rather than a failure state.
- TWO SIGNALS, AND THE RATIO IS THE POINT. `directory_views` is passive, complete and frictionless (measurement). `market_interest` is a consented opt-in (permission to come back). 400 arrivals with 240 opt-ins is a city worth opening; 400 with 15 is not, and arrival counts alone cannot tell them apart. The opt-in is nearly free because the directory sits behind login, so it is one tap and not a form.
- The waitlist exists for RE-CONTACT, not measurement. A diagnosis is one-and-done — a season does not change — so without a consented channel the demand we measured simply evaporates before the city opens. It doubles as the designer-recruiting pitch ("240 people here are waiting").
- BLOCKER: nothing in this stack can send that notification. There is no email provider wired up and Clerk's auth mail is not usable for it. A waitlist that cannot be notified is a dead table — shipping the directory means shipping a sender with it.
- Travel intent is covered by NOT locking the city filter to the user's location, so someone planning a trip just browses that city. `directory_views.viewed_city` records what they looked at, not where they are. Asking about travel dates would be a multi-field form on a dead-end screen serving a thin slice of users; revisit only when several cities are live.
- `designer_clicks` is service-role only and written through an API route, never by the client. It is the billing basis, so a client that could insert would be defrauding a paying partner — same tamper-proofing argument as diagnoses. Rows are kept individually rather than as a counter because showing a designer a timestamped log is a different conversation from telling them a number they cannot verify.
